Brief gaps and answers

What the brief explicitly asks that you might miss, and how to answer.

1. Cost and commercial

Brief asksAnswer
"Cost of the humans who keep it running" Estimate 0.5 FTE support at scale (£30k/year). Schema review: 2 hours/week PM time. On-call rotation shared with platform team. Total human cost at 50 clients: ~£50k/year
"Who pays when a client triples their query volume or asks for hourly instead of daily?" Overage pricing. Base tier = nightly + 50GB/month. Above that, £X per GB. Hourly = premium tier at 2x price. Volume spike mid-contract: we alert, they upgrade or we throttle
"How does it interact with the tiers and modules we sell today?" New add-on, not included in current tiers. Existing clients pay extra. New enterprise deals can bundle it. No cannibalisation — this serves a need current tiers don't
"A data product with attractive gross margin at ten clients and none at a hundred" At 10 clients: ~60% margin (low egress, shared support). At 100: risk is egress + support load. Need overage pricing + self-service to stay above 40%. If margin drops below 30%, pricing is wrong

2. Technical

Brief asksAnswer
"Clients with no warehouse" Offer Solution 4 (direct access) — they connect Tableau/Power BI directly. Or: we host dashboards for them (future phase). Or: they use CSV downloads (current state, free)
"Historical backfill and reload" Quoted separately. Estimate £2-5k per year of history. One-time job outside normal SLA. Contract language: "Base product includes trailing 12 months. Additional years quoted separately. Backfill requests within 30 days of contract signature"
"What happens when a client's pipeline breaks at 3am and they cannot tell whether the problem is ours or theirs?" Clear boundary: if file landed in their bucket with correct checksum, it's theirs. If not, it's ours. We publish to status page, PagerDuty alerts on-call, client portal shows export status. Support SLA: acknowledge within 4 hours during business hours
"Where would you build, and where would you buy?" Build: export jobs (our data, our logic), versioning layer (core IP), config UI (product surface). Buy: scheduler (Airflow Cloud), monitoring (Datadog), object storage (AWS S3), alerting (PagerDuty)

3. Version and change control

Brief asksAnswer
"Where does that boundary live, who owns it?" Boundary = the versioned views. Data PM owns the version policy. Eng owns implementation. Schema changes that touch export tables need Data PM sign-off before merge. Weekly sync: Eng + Data PM
"What does it cost to maintain?" ~4 hours/week PM time (schema review, changelog, client comms). ~2 hours/week eng time (view maintenance, testing). At scale: may need dedicated Data PM (0.5-1 FTE)
"Restatements or late-arriving corrections to data a client has already consumed" Issue correction file with _correction_YYYYMMDD suffix. Client's pipeline must handle this (documented in onboarding). We do NOT guarantee data is final — we guarantee schema and timing. Corrections are normal business, not SLA breaches
"What has to change in how engineering teams work, and how do you make that stick?" PR template checkbox: "Does this change exported schema?" If yes, requires Data PM review. Enforced by CI check. Make it stick by tying to outcomes they care about: no 3am pages, no angry client calls, no "why did this break?" investigations

4. Governance

Brief asksAnswer
"Minimisation and what you would withhold or mask" Default masked: resident phone, email, bank details. Photos: separate add-on, not in base. Vulnerable tenant flags: encrypted or excluded. Client can request unmasked PII with explicit DPA clause accepting responsibility
"The obligations that come with social housing data" Awaab's Law: damp/mould data must be trackable — we include this. Regulator returns: we can provide in RSH format as custom engagement. Vulnerable tenant data: highest sensitivity, explicit justification required

5. Making it real

Brief asksAnswer
"How you would validate demand beyond the loudest client" Survey top 20 clients: "Would you pay £X/month for automated data export?" Need 10+ yes. Talk to churned clients: was data a factor? Check lost deals: did competitor win on data access? If only one client wants it: don't build a product. Quote it as custom work for them. They fund it, they get it first. Only productise if 5+ confirmed buyers
"How you would measure whether it works for us and for them" For us: gross margin >40%, support tickets <2/client/month, onboarding <5 days. For them: export arrives on time 99.5%, <1 schema-break complaint per quarter, NPS for data product >40

Unexpected questions they might ask

QuestionWhat they're testingAnswer
"What if we tried versioning before and it failed?" Can you diagnose org problems, not just tech? Ask: was it a tech failure (views broke) or a process failure (people bypassed it)? Usually it's process. The fix isn't better views — it's tying schema review to outcomes eng cares about: fewer incidents, fewer support calls. No enforcement = failure
"Our eng team hates process. How do you make this stick?" Do you understand eng culture? Don't frame it as process. Frame it as protection. "This PR check saves you from a 3am page when a client's pipeline breaks." Tie it to outcomes they want. Keep it lightweight — one checkbox, not a 10-step approval chain
"A client wants their custom fields in the export. Now what?" Can you say no? Can you scope? Three options: (1) If useful for others, add to standard scope — free. (2) If truly custom, quote separately — client funds it. (3) If not feasible, say no. Push back: "Here's standard scope. Custom is quoted work. What's the business need?"
"What if a client's pipeline breaks and they blame us?" Do you understand SLA boundaries? Audit trail proves exactly what we sent, when, what format, what checksum. If file landed correctly, it's their pipeline. We don't debug their dbt. Clear SLA: "We guarantee delivery. We don't guarantee your transformation works." This is in contract and onboarding
"How do you handle a correction to data we already exported?" Do you understand real-world data ops? Issue correction file: repairs_correction_20260915.parquet. Their pipeline must handle this — documented in onboarding. We do NOT re-export full file (expensive, confusing). Corrections are normal. If frequent, that's a platform quality issue
"What's the 1-year cost to run this at 50 clients?" Can you think commercially? Quick math: £320 COGS × 50 clients × 12 months = ~£192k/year. At £2k/mo revenue × 50 × 12 = £1.2M revenue. Gross margin ~84%. Main risk is support cost scaling — that's why standardisation matters
"Why wouldn't we just use Fivetran/Airbyte?" Do you understand the architecture? They pull from sources via our transactional API — slow and expensive for bulk. We'd pay compute for every API call. Our solution: we push files directly to client buckets. No API load, no rate limits, predictable cost. Different architecture. Also: they don't solve versioning — we still need the publication layer
"We shipped a bug that corrupted last week's data. How do you handle a restatement?" Do you understand data ops recovery? Issue a versioned replay: new delivery labelled replay_2026-09-10_status_bug_fix. Document: what was wrong, date range affected, who authorised. Client re-ingests — their pipeline upserts on primary key + timestamp. Audit trail preserved. Never silently overwrite — they may have filed regulatory reports from old data
"How do 50 clients on different versions work?" Can you think about scale? Max 2 versions live (N and N-1). Version registry tracks which client is on which. Automated nudges when N-1 support window closing. At 50 clients: same two versions, same code paths, just config per client. If client misses migration window, they're on unsupported version — contractually their risk. This is why we don't support unlimited versions

The "already paid for data" conversation

This is the hard commercial conversation. Script it.

Client saysYou say
"We already pay for our data" "You pay for the platform — access, features, support. And you CAN download CSVs yourself anytime, that's included. This new product is different: automated delivery to YOUR bucket, versioned schema, SLA, machine-readable format. That's the value-add with real costs behind it"
"But it's OUR data" "Absolutely. And you can access it anytime via the platform. This product is about how you get it: automated, reliable, machine-readable, with a schema contract. That's the value-add"
"Competitor X includes it" "Do they? What's the SLA? Is it versioned? Do they support your warehouse? Happy to compare. If they genuinely offer this, that's a pricing conversation — but I'd want to validate the comparison is apples to apples"
"We'll just use the API" "You can. It's included. But the API is transactional — one record at a time. For bulk analytics, it's slow and expensive for both of us. The brief literally says 'using them that way is slow and expensive.' This product solves that"

When clients say no during validation

If validation reveals clients won't pay, that's valuable signal. Here's how to handle each objection.

ObjectionWhat it tells youYour response
"We're not willing to pay" Price or value mismatch Dig deeper: is it "not £2k" or "not anything"? Test lower tiers or different packaging. If genuinely no budget, deprioritise this segment
"We're happy with bespoke CSVs" Pain not sharp enough Probe: How often do they break when we ship changes? How long to get a new extract? "Happy" often means "tolerating." Find clients with sharper pain
"Why should we pay? It's our data" See data as right, not service You're not paying for data — you're paying for the managed service: automation, stability, versioning, security, support. That has real cost
All clients say no No market exists Kill it. Validation worked — better to learn now than after building

The meta-answer for the interview

"Validation failure isn't project failure — it's the system working. I'd either adjust the offer (different price, scope, packaging), find different customers (maybe SMBs don't value this but enterprise does), or kill it. The worst outcome isn't 'no' — it's building something nobody pays for."

Why API is bad for bulk extraction

The brief says: "The APIs are transactional: built for integration and workflow, not for bulk analytical extraction. Using them that way is slow and expensive for both sides."

Here's why:

ProblemWhat happens
Rate limits API has limits (e.g., 100 requests/minute) to protect the platform. At 100 req/min, getting 1 million records = 10,000 minutes = 7 days
Pagination API returns 50-100 records per call. 1 million records = 10,000+ API calls
Latency per call Each API call takes ~200ms network round-trip. 10,000 calls × 200ms = 33 minutes just waiting
Authentication overhead Each call validates token, checks permissions, logs access. That overhead × 10,000 calls
Server load 10,000 API calls = 10,000 times the server wakes up, runs a query, formats JSON, sends response
Cost to us Every API call costs compute. Bulk extraction via API = massive compute bill
Cost to them They need to write code to handle pagination, retries, rate limit backoff, reassembly

Example: Getting all repairs for a year

MethodHow it worksTimeCallsCost
API GET /repairs?page=1, GET /repairs?page=2, ... page 10,000 7+ hours (with rate limits) 10,000 High (compute per call)
File drop One scheduled job writes repairs.parquet to S3 5 minutes 1 job Low (one query)

Interview answer: "The API is transactional — built for 'get me this one repair.' Using it for bulk extraction means 10,000+ API calls, hitting rate limits, hours of runtime, and high compute costs on both sides. File drop runs one query, writes one file, delivers gigabytes in minutes. It's the right tool for the job."

These test prioritisation, stakeholder management, and business thinking — not technical knowledge.

Explain what's possible, offer interim solutions (manual extract for now, automated later). Never promise what you can't deliver — own the conversation early

Prioritisation frameworks, saying no, communicating trade-offs Phase 0 is a blocker — nothing else ships securely without it. Frame it as unblocking everything else, not competing with it. Bring engineering into the legal conversation. Make it their problem too, not a mandate from above. Find scope they can commit to
A client threatens to leave if they don't get data export in 4 weeks. Phase 0 alone takes 6. What's your move? Crisis management, creative problem-solving, knowing when to say no Be honest: "We can do a secure manual extract now, or wait 6 weeks for automated. We won't ship something insecure." Offer the interim, protect the relationship, don't cave on safety
How do you measure success for Phase 0? It has no direct revenue. Defining metrics for enabling/foundational work Pen test pass rate. Time to answer security questionnaires. Number of enterprise deals unblocked. Reduction in manual extract requests. These are leading indicators of revenue
You've shipped Phase 0. How do you know it actually works? Defining "done," acceptance criteria, validation Automated isolation tests pass. External pen test passes. Can fill out client security questionnaire with evidence. First secure export delivered without incident
The sales team keeps promising custom data fields. How do you handle scope creep? Product discipline, managing commercial pressure Define what's in the standard product vs custom. Custom is quoted separately. Sales needs a pricing framework, not a blank cheque. Work with commercial to create it
What's your 12-month roadmap for this data product? Walk me through it. Strategic thinking, sequencing, phased delivery Phase 0 (multitenancy): months 1-2. Phase 1 (scope definition): month 3. Phase 2 (versioning): months 4-5. Phase 3 (delivery mechanism): months 6-7. Phase 4 (governance): ongoing. Phase 5 (productise): months 8-12
You have to cut scope. What do you drop from Phase 0 and why? Trade-off decisions, understanding what's truly essential Keep: RLS on export tables, pen test, automated tests. Cut: full database coverage (do export tables only), fancy monitoring (basic logging is enough for MVP). Secure the exit path first
How do you get buy-in from engineering when they'd rather build features? Influence, storytelling, making the case Show the cost of not doing it: blocked deals, breach risk, fines. Show the benefit: once done, we can sell to every enterprise client. Make it a "build once, unlock many" story
A competitor launches a data export feature next month. Does that change your plan? Competitive response, staying focused vs reacting Not fundamentally. We don't rush and ship something insecure because a competitor moved. We might accelerate, but we don't skip Phase 0. Speed without safety is a liability

Phase 1 — scope questions

How do you support different client requirements without building custom code for each?

LayerWhat it coversHow it's handled
Standard scope The 80% that most clients need (repairs, properties, compliance, work orders) Built once, available to all. This IS the product
Configuration Delivery schedule, file format, destination, which tables they want from the standard set Config per client — no code, just a settings row
Custom fields/tables The 20% where one client has a unique ask Quoted separately, funded by that client, or "no"

The product discipline: You're NOT trying to support every requirement. You define what's IN the product (standard scope), what's OUT (custom or "not available"), and price the difference.

2. Technical considerations How to build it, what infrastructure Phase 0 (multitenancy/RLS), Phase 3 (export jobs, S3, scheduling). 8-12 weeks. Tenant isolation is critical

A client keeps triggering manual exports 10 times a day. What do you do? Edge cases, abuse, product limits "That's abuse. Options: rate limiting, charge per export, or ask why. Maybe they need real-time — that's a different tier."

Phase 0 — technical questions

You need to understand these, but don't get lost in the detail. Know enough to be credible, focus on decisions.

QuestionHow to answer
What is multitenancy? One system, many clients, each sees only their own data. Not separate databases per client
Why can't we just filter in queries? Human error — one missed WHERE clause = data breach. RLS enforces it at database level, no exceptions
How long will Phase 0 take? Depends on current state. Need to audit first. If tenant IDs exist: 4-6 weeks. If gaps: 8-12 weeks
What's the risk of not doing it? GDPR fines (£17.5M or 4% turnover), client lawsuits, contract termination, reputation destroyed
What if tenant IDs don't exist on some tables? Then we have a data problem first. Need to backfill or restructure. This is why we audit before estimating
What about reference/lookup tables shared across clients? Those don't contain client data — they're fine to share. Example: a list of repair categories. But anything with client-specific records needs isolation
What about historical data that was never tagged with tenant? Risky. Options: backfill if possible, exclude from exports if not, or accept that old data can't be exported safely
How do you test multitenancy without using production data? Create test tenants with synthetic data, run queries as each tenant, verify isolation. Also: security team does pen testing
Can you guarantee zero data leakage? No one can guarantee zero. But RLS is the industry standard, and we'll have automated tests + pen testing + monitoring. That's the defensible position
What are automated tests for multitenancy? Create test data for Tenant A and B. Query as Tenant A. Assert: you see ONLY Tenant A's data, zero rows from B. Run on every deploy
What is pen testing? Security experts try to break your system — find ways to access data they shouldn't. External pen test is more credible to clients
Is RLS industry standard? Yes. Used by Salesforce, AWS, most modern B2B SaaS. Built into PostgreSQL, SQL Server, Oracle, Snowflake

The killer question (be ready)

"If multitenancy is so critical, why hasn't it been done already?"

How to answer:

"Probably because manual extracts worked for the clients they had, and the security risk wasn't visible until enterprise clients started asking hard questions. That's normal — you don't build infrastructure until you need it. Now they need it."

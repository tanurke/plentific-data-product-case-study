Plentific · Data Product Manager case study

Final proposal · September 2026

Plentific Data Delivery Drill-down appendix ↓

Executive recommendation

Build a stable data contract, not a bigger export.

The brief points to a broader client need than simply receiving a nightly full export: large clients need dependable, governed access to Plentific data that their own data platforms can build against without Plentific's product velocity becoming their outage. My recommendation is to create a client-facing Plentific Data Delivery product, enabled by an internal publication layer that deliberately decouples external contracts from internal data structures.

First deliveryDaily incremental Parquet + initial snapshot
BoundaryVersioned external data contracts
CommercialEnterprise module + usage guardrails
Deliberately laterNative sharing, higher cadence, AI/MCP

The product decision: keep Plentific free to change internally, while making the external publication model deliberately boring, stable and trustworthy. Transport can evolve; the contract is the durable product.

1. Reframe the problem

Today Plentific controls the client experience: fixed dashboards, fixed-column downloads and transactional APIs. A warehouse feed changes that relationship. The moment a client builds production pipelines against Plentific data, the schema becomes an interface with a contract attached.

Client jobJoin Plentific repairs/compliance data to housing, finance and CRM data and answer questions Plentific cannot anticipate.
Plentific constraintContinue shipping product changes quickly; internal implementation cannot become an external compatibility promise.
Product implicationCreate a stable publication boundary and standardise delivery, rather than creating a bespoke export per enterprise client.
Recommended delivery pattern

Clients need a complete, dependable view of their Plentific data on a predictable schedule. I would provide an initial historical load followed by scheduled incremental updates covering new, changed and deleted records. This gives clients a reconstructable current view while reducing unnecessary data movement and making recovery easier. Where an existing client system requires a full scheduled extract, that can be supported as an alternative delivery mode rather than being the default for every client.

Funding storyFund the minimum foundation through 2–3 strategic design partners and an explicit enterprise revenue case — not as an open-ended warehouse rebuild.

2. Product & architecture

I would not expose the existing internal warehouse directly. It is an input to the product, not the product contract. Plentific needs an external publication layer whose semantics can remain stable even when internal tables, services and workflows change.

Internal Plentific

  • Product services
  • Operational data
  • Internal warehouse
  • Free to evolve quickly
→

External publication layer

  • Canonical client-facing entities
  • Tenant policy / isolation
  • Versioned contracts
  • Quality + lineage + classification
  • Incremental change semantics
→

Client delivery

  • Parquet + manifest
  • Dedicated secure destination
  • Client loads Snowflake / Databricks / BigQuery / Synapse / lake
  • Later: native shares / agent tools

Where I build: Plentific owns the external semantic contract, tenancy rules, compatibility, quality and observability — these are differentiating trust capabilities.

Where I use managed capability: object storage, encryption/KMS, secrets, identity, orchestration and monitoring should use existing cloud/platform capabilities where practical. Do not build commodity infrastructure for its own sake.

3. First shippable version

MVP proposition

Initial historical snapshot + daily incremental, versioned Parquet datasets delivered to a dedicated secure cloud-storage boundary, with a machine-readable manifest and a documented contract.

What is in

  • Small standard domain set chosen with design partners — likely work orders/repairs, assets/locations, bookings/appointments, compliance/inspections and selected financial/work-order attributes. Exact scope is a discovery decision, not something I would invent from the brief.
  • Initial backfill followed by changed records only: inserts, updates and explicit deletion/tombstone events.
  • Idempotent ingestion semantics: stable business key + revision/update timestamp so a client can safely replay a batch.
  • Manifest per delivery: dataset, contract version, extraction time, watermark, file/row counts, checksums and completion state.
  • Operational controls: retries, replay/backfill, audit log, freshness monitoring and client-visible incident communication.
  • Documentation: field meaning, type, nullability, identifiers, timestamp semantics, enumerations, delete/correction behaviour and examples.

What I explicitly do not build yet

  • Per-client schemas or transformations
  • Streaming / CDC as the default
  • Every field, attachment, photo or free-text note
  • Dozens of warehouse-specific connectors
  • Arbitrary client SQL against Plentific infrastructure
  • A self-service semantic modeller
  • AI-generated decisions inside the MVP

4. Change control: the part that makes or breaks the product

My highest-weighted design decision is the external contract boundary. An internal schema change should only become a client change if Plentific deliberately changes the external contract.

ChangeExamplePolicy
Compatible additiveNew nullable fieldSame major contract; changelog and automated compatibility tests
Semantic riskNew enum/status valueContract test + impact review; document unknown-value behaviour
BreakingRename/remove field, type change, key semantics change, meaning changesNew major contract version
Correction/restatementYesterday's completed repair is corrected todayPublish a new record revision; do not silently rewrite a previously delivered batch
DeletionRecord must no longer appearExplicit tombstone/delete event and documented handling
Proposed operating policy — validate in pilot

Support current and previous major contract versions only (N / N−1), dual-run breaking versions during migration, and start with a minimum 180-day deprecation window for enterprise clients unless security/legal requires faster action. These are product-policy hypotheses, not facts from the brief.

How I avoid slowing engineering down

I would not create a governance meeting every time a team changes a table. The contract is enforced as code: schema/semantic contract tests run in CI/CD; teams get a clear failure only when a change affects an external promise.

  • Domain engineering owns source meaning and flags intended behavioural changes.
  • Data/platform engineering owns the publication mechanism, quality controls and compatibility tooling.
  • Data Product owns external scope, contract lifecycle, deprecation policy and client communication.

This turns governance from “more process” into protection from client incidents, emergency migrations and support escalations.

No row leaves Plentific until the tenant boundary is demonstrably safe. RLS can be an important control, but it is not the whole tenancy strategy.

6. What I would sell

Commercial recommendation

Enterprise Data Delivery add-on (or included in the highest enterprise tier) with a predictable annual platform fee, daily delivery and an agreed volume/backfill envelope. Higher cadence, exceptional reloads, unusually high egress and native warehouse sharing become premium allowances/add-ons — not hidden cross-subsidies.

The client conversation: “You are not paying to own your data. You are paying for a managed, secure, versioned and supported interface that continuously publishes it in a form your production data platform can safely consume.”

Why not pure usage pricing?

Enterprise customers need budget predictability, while Plentific needs protection from outlier cost-to-serve. I would therefore price the commercial proposition predictably and use usage as a guardrail, not make every GB or query the buying experience.

Unit economics

Measure COGS per client before final pricing:

COGS / client / month =
  transformation compute
+ retained delivery storage
+ network egress
+ orchestration + observability
+ support / on-call allocation
+ security & compliance allocation
+ backfill / replay cost
Illustrative economics — not Plentific actuals

If measured all-in COGS is £400/month and the target gross margin is 80%, the price floor is £2,000/month: £400 ÷ (1−0.80). I would then test willingness-to-pay and strategic value rather than treating this formula as the final price.

The metric I would watch hardest: human support minutes per client. Cloud storage can be cheap; bespoke schemas, custom schedules and manual recovery destroy margin. Standardisation is therefore both an architecture strategy and a gross-margin strategy.

7. Sequence: validate, de-risk, then scale

I would use evidence gates rather than pretend I know the exact engineering calendar before discovery.

Gate 0
Prove a repeated problem
Interview strategic clients; analyse API/download/manual-extract behaviour; map warehouse stacks and top requested domains.
Exit: repeated need across multiple clients + credible willingness to pay.
Gate 1
Make publication safe
Tenant isolation, classification/minimisation, external contract model, quality/lineage, audit and security evidence.
Exit: security/data review passes; no known cross-tenant path.
Gate 2
Paid/design-partner pilot
Small domain set, snapshot + daily incremental Parquet, manifests, replay, docs.
Exit: 2–3 clients ingest automatically and use the data for real downstream work.
Gate 3
Repeatable beta
Onboarding playbook, observability, change lifecycle, operational ownership and commercial package.
Exit: new client onboarding does not require new code.
Gate 4
GA
Entitlements, support model, published SLO/SLA, version policy and measured unit economics.
Exit: healthy gross margin and reliable operation at growing client count.
Later
Expand by evidence
Higher cadence, native warehouse sharing, bulk pull options, AI/agent access.
Trigger: repeated demand and economics justify added product surface.

What if the demand is one loud customer?

I do not build a platform product from one feature request. I validate the underlying job with other strategic clients and usage evidence. If the need is genuinely unique, I either treat it as separately funded bespoke work with a clear maintenance boundary, offer a safe interim extract, or say no. I would not create permanent product complexity disguised as “enterprise flexibility”.

9. Forward-looking: make the data contract agent-ready

After the foundation is trusted

The next interface may be an agent, not another ETL pipeline.

The same governed publication layer can become a safe source of context and tools for AI agents. The key is not to let an LLM bypass the controls we just built. MCP should sit on top of the external contract, not on top of raw internal tables.

What MCP adds

Model Context Protocol (MCP) is an open standard for exposing tools and context to AI applications. That creates a future path for a Plentific MCP service that makes approved repair/compliance capabilities available to agents without every client inventing a bespoke AI connector.

Governed publication layer

Same tenant policy, semantics, quality, lineage and version lifecycle as the data product.

→

Plentific MCP / agent tools

Read-only, scoped tools and resources — not unrestricted SQL.

→

Client or Plentific agents

Reason across repairs, compliance and approved client context; actions remain governed.

High-value agent use cases

Use caseExampleWhy the data product matters first
Compliance risk triage“Which open damp/mould cases are approaching a required service deadline, and what evidence is missing?”Agent needs trusted timestamps, status semantics, lineage and tenant-safe access
Repair investigation“Why was this repair delayed?” Agent gathers status history, appointments, contractor events and exceptions and produces a traceable summary.Stable identifiers and versioned meanings prevent hallucination-by-data-drift
Data onboarding assistantExplain fields, generate example dbt mapping, diagnose a failed load from the manifest and contract.The contract and operational metadata become agent-readable documentation
Schema migration assistantCompare v1 → v2 and generate a proposed client migration/test plan.Explicit contract diffs give the model deterministic evidence
Natural-language analytics“Show emergency repair completion trends by region.”Queries should resolve against curated semantics rather than raw operational schema

Agent guardrails from day one

Read-only first. Start with retrieval/explanation tools. Do not let the first agent close a repair, alter compliance state or publish a regulatory return.
Deterministic policy for deterministic obligations. Deadline calculations, tenancy filters and entitlement decisions remain coded rules; AI can explain or prioritise them, not redefine them.
Least privilege + tenant-scoped auth. The agent sees exactly what the calling principal is allowed to see. Tool calls are logged and rate-limited.
Human approval for high-impact actions. If action tools arrive later, sensitive state changes require explicit approval and a complete audit trail.
Evaluate before scaling. Build a domain evaluation set: factual accuracy, source traceability, missed-risk rate, false-alert rate and permission-boundary tests.

This future path is deliberately not in the MVP. It is an option created by getting the boring fundamentals right now. The stronger the external contract, the easier it becomes to support files, native warehouse sharing, APIs and agent tooling without creating four inconsistent versions of Plentific data.

Technology note: the current MCP specification and major agent SDKs support remote MCP tool integration and emphasise explicit authorization/approval boundaries. Any production design would be validated against the protocol/security guidance in force at implementation time.

10. Drill-down appendix — choices I expect to defend

Why not just expose the existing warehouse?

Because then internal implementation becomes a public API. Internal refactors, data-model clean-up and product workflow changes become breaking client changes. It also puts the highest-risk tenancy/security surface closest to a warehouse never designed for external scrutiny. I would expose a deliberate publication layer instead.

How important is RLS for tenancy?

Important, but not sufficient alone. I want tenant-scoped publication and delivery boundaries, least-privilege credentials and negative isolation tests. RLS/policy enforcement is defence in depth; I would not make one filter the sole barrier between two housing associations' resident data.

Engineering does not want more process. How do you get buy-in?

Automate it. Put contract compatibility tests in CI/CD and make the external boundary clear. Engineers keep changing internals freely; they only need to engage when a change would break a sold client promise. The pitch is fewer incidents and emergency migrations, not “more governance”.

Is object-storage delivery the only solution?

No. Native sharing, bulk APIs and managed pipelines can all be right in different contexts. I choose files first because they are the broadest interoperable option and keep the irreversible decision — the data contract — independent from a warehouse vendor. I would change the mechanism when measured demand proves a better option.

What if Snowflake clients strongly prefer zero-copy sharing?

Keep the same external contract and add Snowflake-native sharing as a premium delivery adapter once enough strategic demand exists. The schema, security policy and version lifecycle should not be rewritten for Snowflake.

How would I support a client that requires a full scheduled extract?

The standard product would be an initial historical load followed by incremental updates, because that is more efficient and easier to recover at scale. If a client's existing ingestion technology genuinely requires a complete scheduled snapshot, I would support that as an alternative delivery mode with clear volume, operational and commercial guardrails rather than force the client to redesign immediately.

How do we know a 3am failure is ours or theirs?

Each delivery has a manifest, checksum, watermark, row/file count, contract version and completion state. Plentific monitors production and delivery; the client can independently verify what landed. The support boundary becomes observable rather than anecdotal.

How do late corrections and restatements work?

Publish a new revision of the same business entity with an updated revision/update timestamp. Client upserts idempotently. For exceptional historical restatement, issue a versioned replay/backfill with a reason and audit record. Never silently mutate a file the client may already have reported from.

Who pays when a client wants hourly instead of daily?

The client asking for the higher service level. Cadence changes compute, operational load and incident expectations, so it belongs in a premium allowance/tier. Daily clients should not subsidise hourly clients.

What happens at 100 clients?

The architecture survives only if a client is configuration, not code. One contract per supported version, automated tenant policy, standard destinations/adapters, automated onboarding checks, shared observability and explicit support/version limits. If each client gets a custom schema, the product has already failed before client 100.

What would make you stop or change direction?
  • Demand does not repeat beyond one or two bespoke accounts.
  • Willingness to pay does not cover measured cost-to-serve and platform investment.
  • Clients overwhelmingly need a different freshness/mechanism than the proposed MVP.
  • Security isolation cannot be demonstrated to an enterprise standard on the current foundation.
  • Support effort per client remains high because the supposedly standard product is actually bespoke.

Decision in one sentence

Make Plentific's internal product fast-moving and its external data contract slow-moving: build the governed publication boundary first, launch a standard daily incremental data-delivery product on top, prove the economics with design partners, and then reuse that same contract for richer warehouse and agent interfaces.

Assumptions I would validate before committing

  • How many strategic clients have the same job, their warehouse/lake technologies and acceptable freshness.
  • Actual data volumes, change rates, retention/backfill needs and current manual/API cost-to-serve.
  • Existing tenancy controls in the warehouse and whether a separate publication store/account is warranted.
  • Which fields are genuinely required, which contain personal/special-category/high-risk free text, and the lawful/contractual basis for export.
  • Current cloud platform, orchestration/observability capabilities and whether cross-cloud egress is material.
  • Willingness to pay, current commercial entitlements and what existing contracts imply about data access.

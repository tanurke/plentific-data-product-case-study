Opening

Build a data contract, not a bigger export

Plentific Data Delivery: trusted data in the client's warehouse

Clients ask for "a nightly batch export."

Their actual need: dependable, governed access to Plentific data that their pipelines can safely depend on.

What I see in this problem

The brief describes two products, not one:

  • Product A: Internal foundation — tenant isolation, governance, contract layer
  • Product B: Client-facing delivery — the thing they buy

The delivery mechanism (files vs API vs sharing) is the easy part.

The main problem to solve is: how does Plentific keep shipping fast while clients need stability?

That's why I weighted version/change control highest.

Why files first?

  • Universal: Works with any warehouse (Snowflake, Databricks, BigQuery, on-prem)
  • No lock-in: Client isn't tied to our platform choice
  • Cheaper: Files can be compressed, lower egress costs
  • Auditable: Clear record of what was sent, when, to whom
  • Versionable: Each delivery is immutable — easy to track schema versions
  • Recoverable: Client can re-request any past delivery

Add native sharing later for Snowflake clients who want it.

Architecture

Two products, sequenced deliberately

PRODUCT A: Internal Foundation ENGINEERING/PLATFORM PRODUCT ───────────────────── ───────────────────── Internal warehouse → Define scope (which tables) ↓ ↓ Publication layer (views) → Define contract (schema) ↓ ↓ Tenant isolation (RLS) → Versioning policy ↓ ↓ Quality + lineage → Change classification ━━━━━ STABLE BOUNDARY ━━━━━ ↓ PRODUCT B: Client Product ┌─────────────────────────────────────────────┐ │ Versioned datasets │ │ Secure delivery → S3/Azure/GCS │ │ Delivery summary + monitoring │ │ Documentation + changelog │ └─────────────────────────────────────────────┘ ↓ Client warehouse

Why not expose the internal warehouse directly?

Because then internal refactoring becomes an externally breaking change. Engineering loses the freedom to move fast. That contradicts the brief's core constraint.

How to fund invisible platform work

Don't ask for 6 months of platform investment. Find 2-3 paid design partners, agree price and scope, fund the minimum platform needed to deliver.

Platform investment becomes a new data product — revenue enablement, not internal overhead. Productise it.

Deep Dive

Version and change control

How Plentific keeps shipping while clients stay stable

Change classification

New nullable fieldSame version
New enum valueReview
Rename/remove fieldNew version
Type changeNew version
Meaning changeNew version

My policy

  • 180-day deprecation for breaking changes
  • N and N-1 only — not forever
  • Dual-run during migration
  • CI checks if source changes affect contract

How engineering stays fast

Internal tables change freely. The publication layer translates to the stable external contract. Engineers don't need approval to refactor — only when changes affect the published schema.

"Compatibility is a promise, not immortality. Clients get predictable migration time; we don't support every historical schema forever."
Governance

Security and tenant isolation

No data leaves until this passes

Isolation model

  • Row-Level Security (RLS) at database level
  • Separate export job per tenant
  • Separate storage destination per tenant
  • Automated cross-tenant tests on every deploy
  • External pen test before first client

Summary

My recommendation

DON'T → Expose Plentific's warehouse ↓ DO → Create a stable external contract ↓ DELIVER → Daily incremental, open format ↓ PROTECT → Tenant isolation + versioning ↓ MONETISE → Paid module, ~£2k/month ↓ EXPAND → Native sharing when demand proves it

Plentific keeps moving quickly.
Clients get an interface they can trust.

Why this wins

  • Competitors offer manual CSV and transactional APIs — no one offers versioned automated delivery
  • Plentific already has API versioning — extend it to bulk data (6-12 month head start)
  • Standardisation protects margin at scale

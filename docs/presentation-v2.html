Architecture

Two products, sequenced deliberately

PRODUCT A: Internal Foundation ENGINEERING/PLATFORM PRODUCT ───────────────────── ───────────────────── Internal warehouse → Define scope (which tables) ↓ ↓ Publication layer (views) → Define contract (schema) ↓ ↓ Tenant isolation (RLS) → Versioning policy ↓ ↓ Quality + lineage → Change classification ━━━━━ STABLE BOUNDARY ━━━━━ ↓ PRODUCT B: Client Product ┌─────────────────────────────────────────────┐ │ Versioned datasets │ │ Secure delivery → S3/Azure/GCS │ │ Delivery summary + monitoring │ │ Documentation + changelog │ └─────────────────────────────────────────────┘ ↓ Client warehouse

Why not expose the warehouse directly?

Internal refactoring → externally breaking change. Engineering loses freedom to move fast.

How to fund platform work

Find 2-3 paid design partners. Fund minimum platform to deliver. Revenue enablement, not overhead.

Deep Dive

Version and change control

Change types

Type Notice Version
Additive Changelog Eng decision
Deprecation 90 days + email Warning
Breaking 90+ days + guide New version

Policy hypothesis

  • 180-day deprecation for breaking changes
  • N and N-1 only — not forever
  • Dual-run during migration
  • CI checks on schema changes

Validate with eng + early clients

How engineering stays fast: Internal tables change freely. The publication layer translates to stable external contract. Engineers don't need approval to refactor — only when changes affect published schema.

Governance

Security and tenant isolation

Isolation model

  • Tenant-scoped publication + RLS/policy
  • Separate destination per tenant
  • Negative tests (cross-tenant queries return nothing)
  • Pen test before first client

Data governance

  • Operational data → Include
  • Free-text notes → Exclude
  • GDPR & export control → Managed via contracts
